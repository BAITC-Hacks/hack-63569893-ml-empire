# Voice Router: покрытие требований и критериев оценки

Дата: 23.09.2026. Объём: клиентское веб-приложение, протокол подключения, документация и изолированный синтетический QA-сервер. **Это не сертификат полного соответствия ТЗ и не прогноз гарантированных баллов.**

1. Предоставленный заказчиком DOCX «HackAlem AI: Voice Router — гибридный голосовой AI-робот с LLM-слоем выбора сценария»: исходные must-have, ограничения и общая шкала 100 баллов.
2. [README стартового набора](../../datas/README.ru.md): предметная область, каталог SC01–SC40, 10 диалогов, 104 dev-реплики, правила общения и прикладная проверка жюри.
3. [Архитектура команды](../../docs/voice-router-architecture.md): выбранные серверные обязанности и разделение ответственности.
4. [Функции frontend](frontend-functions.md): принятый функциональный план. Его ранние примеры событий не заменяют актуальный контракт.
5. [HTTP/WebSocket-контракт](frontend.md): единственный источник имён событий и базовых payload. Расширенные поля панели могут требовать реализации на сервере.

Halyk — заказчик/трек и визуальный ориентир. **Saqta Insurance вымышлена**, данные синтетические, дата среза — `2026-10-01`. Нельзя подменять данные страхового набора реальными условиями Halyk или представлять приложение как действующий банковский сервис.

### Как читать статусы

- **Клиент реализован**: код обработки/показа есть; это не подтверждение работы внешнего компонента.
- **По данным API**: frontend умеет показать поле, но не вычисляет его и не создаёт отсутствующие сведения.
- **Интеграционная приёмка**: нужен настоящий API, голосовое устройство или проверка всего решения.
- **Backend**: нельзя закрыть изменением frontend; клиент только передаёт/показывает данные.
- **Опционально**: не относится к must-have банка, если отдельно не принято командой.

Конкретные выполненные проверки и открытые пункты — в [чек-листе](frontend-verification.md). Наличие fixture, статичного примера или unit-теста не приравнивается к выполнению реального голосового сценария.

| B02 | Сценарий выбирается на генеративном LLM-слое | Передаёт ввод и показывает source/причины; локального классификатора нет | Реализовать и показать настоящий маршрутизатор; frontend не доказывает, какой алгоритм работает на сервере |
| B03 | Корректный выбор по 40 исходным сценариям | Отображает любые полученные ID/названия, несколько намерений и системные намерения | Проверить каталог, схему, границы, hidden-набор; точность — результат модели/сервера |
| B04 | После каждой реплики видны сценарий, обоснование, альтернативы и задержки по этапам | Панель и связь по `turn_id` реализованы | Сервер обязан выдавать решение/тайминги после каждой реплики, включая продолжение/подтверждение |
| B05 | Русский, казахский и смешанная фраза; язык может меняться | RU/KK UI, `mixed`, Unicode, раздельные языки запроса/ответа | Качество распознавания, понимания и ответа на нужном языке проверяется с провайдерами |
| B06 | Реальный ввод и данные, не один записанный демо-сценарий | Обычный режим обращается к API; fixture/пример помечены отдельно | Реальный LLM в содержательной точке решения и работа с данными |
| B07 | Необратимые действия только после подтверждения | Preview, аргументы, кнопки/голос следующей репликой; UI не выполняет действия | Серверная проверка согласия, идемпотентность, отказ/смена темы/обрыв без исполнения |
| B08 | Передача оператору, когда робот не справляется | Handoff: причина, очередь, контекст, статус — по API | Серверная политика, достоверность статуса и интеграция/честный mock оператора |
| B09 | Explainability и явная неопределённость, не «чёрный ящик» | Причина, альтернативы, оценка модели с предупреждением, clarify/handoff | Краткие реальные причины по данным; не выдавать hidden reasoning или некалиброванную оценку за вероятность |
| B10 | Только синтетические данные; реальные записи звонков запрещены | Предупреждение, явное действие для записи, маскирование повторного показа/экспорта | Серверные логи/провайдеры/хранилище тоже должны соблюдать ограничение; клиентское маскирование не обезличивает произвольный реальный разговор |
| B11 | Секреты не оказываются в браузере | Публичный адрес API, безопасные сообщения по коду, нет провайдерских ключей | Секреты/аутентификация/CORS/origin/доступ к сессии на сервере |
| B12 | Одна команда запуска и README | Есть одна команда **клиент + QA fixture**, инструкция реального API, матрица и чек-лист | Одна команда для **полного** backend + frontend + данных/провайдеров пока не закрыта |
| B13 | Диалог до 10 реплик | История/трассы связаны с отдельными turns, контекст не должен стираться | Прогон не менее 10 реплик с реальным API и сохранением серверного состояния |
| B14 | Реальные замеры задержки; 500 мс router / 1,5 с end-to-audio — ориентиры | Этапы, browser/server разделены, медианы и количество измерений | Замер живого голоса на устройстве и проверка секундомером; достижение порогов не гарантируется |
| B15 | Не хардкодить соответствия проверочных реплик сценариям | В production UI маршрутизации нет; детерминированные маршруты только в явно отдельном QA fixture | Проверить backend; fixture не использовать для оценки точности или как финальную демонстрацию |

## 2. Полный функциональный frontend-план

| ID / раздел плана | Функция и критерий готовности | Реализация и граница |
| --- | --- | --- |
| F01 / 2.1 | Начать звонок, получить ID | `POST /sessions`, проверка формы, сохранение метаданных; сервер должен создать сессию |
| F02 / 2.1 | Завершить, сохранив историю; новый звонок всё очищает | Раздельный локальный lifecycle; серверного endpoint завершения/удаления нет |
| F03 / 2.1 | Длительность, состояние соединения, восстановление | Клиентские таймер/статус; reconnect и snapshot; время до reload не выдаётся за серверную длительность без соответствующего поля |
| F04 / 2.2 | Разрешение и явный старт микрофона | `getUserMedia` только по действию; permission/denied/unavailable и резерв. Завершение до `turn.start` отменяет поздний grant без пустого commit |
| F05 / 2.2 | Уровень, выбранное устройство, отключение микрофона | AudioWorklet уровень, список/выбор устройства, безопасное завершение при потере устройства; требуется hardware-прогон |
| F06 / 2.2 | Фреймы и корректный конец записи | PCM16 LE mono 24 kHz, flush перед commit, отсутствие чанков после завершения; тесты + живая проверка тихих окончаний |
| F07 / 2.2, этап 3 | Ручное и автоматическое окончание | Push-to-talk основной; детектор тишины опционально/настраиваемо, ручной резерв; не является STT или intent-логикой |
| F08 / 2.3 | Непустой текст в той же сессии, запрет двойной отправки | Проверка строки, один активный turn, UUID; бизнес-нормализация не на клиенте |
| F09 / 2.3, 9 | Повтор после сетевой ошибки | Ручной возврат текста в черновик; новая отправка только по действию, никогда автоматически; сначала проверить snapshot/действия |
| F10 / 2.4 | Partial/final, язык, исходная mixed-речь, STT-ошибка | Реализованы; фронт не переводит/не переписывает содержание |
| F11 / 2.5 | Автор, язык, время, состояние, ответ, replay, трасса | Реализованы в истории; replay доступен только при фактически полученном аудио |
| F12 / 2.5 | Автопрокрутка без отбирания ручной позиции | Обновляется при нахождении внизу; необходимо повторить на длинной истории/мобильном |
| F13 / 2.6 | Ранний потоковый звук, stop/replay/mute, autoplay fallback | Очередь PCM и управление; браузерные ограничения и физический звук требуют проверки |
| F14 / 2.6 | Первый звук, не время запроса LLM | `playback.started` один раз на исходный ответ; replay/отсутствие звука не создают измерение; hardware-калибровка обязательна |
| F15 / 3 | Подготовка/запись/обработка/ответ/ошибка | Транспортные состояния реализованы; бизнес-этапы показываются только по необязательному `trace.agent_state`, без него не имитируются |
| F16 / 4.1 | Номер, финальный транскрипт, язык, источник, ошибки, clarify | Отдельная трасса каждой реплики; partial/поздние метрики не заменяют соседний turn |
| F17 / 4.2 | Основной/дополнительные/альтернативы, приоритет, причина, оценка | Панель и метаданные каталога; неизвестный приоритет/оценка не выдумываются |
| F18 / 4.1, 6 | Активный != выбранный основной; очередь и приостановленные | Отдельные группы, серверный порядок; explicit `null` не заменяется первым сценарием |
| F19 / 6 | Смена темы, продолжение, возвращение | Отображается source/is_continuation и очередь; предложение вернуться генерирует сервер, клиент не сочиняет его |
| F20 / 4.3 | Статусы слотов found/profile/confirmed/missing/invalid | Простые и структурированные слоты, source/scenario; статус показывается только при наличии данных |
| F21 / 4.3 | Действия requested/preview/awaiting/executing/completed/rejected/failed | Строковые и структурированные формы; запрошенный execute не равен выполненному действию |
| F22 / 7 | Preview с аргументами, согласие/отказ голосом/кнопкой | `action.preview`, новая `turn.text` или аудио; исполнение/очистка pending подтверждаются сервером |
| F23 / 8 | Один уточняющий вопрос | UI показывает полученный ответ/status; число вопросов и смысл контролирует backend |
| F24 / 8 | Оператор: причина/очередь/активная задача/слоты/резюме/статус | Читаемые поля по API; отсутствие данных не заменяется утверждением об успешном переводе |
| F25 / 5 | Миллисекунды, этапы, total, медиана, browser/server отдельно | Реализованы; только конечные неотрицательные значения, количество измерений; голос и текст разделены |
| F26 / 9.1 | Denied/unavailable/unplug/unsupported/неожиданный конец | Обработка/текстовый fallback; сочетания устройства и браузера требуют hardware-теста |
| F27 / 9.2 | Timeout/недоступный API/404/reconnect/дубликаты/старые события | HTTP/ready 10 с, зависший processing/speaking без событий 60 с, 4 retry 1/2/4/8 с, ручное восстановление; без повтора ввода |
| F28 / 9.3 | STT/router/TTS/action error, неизвестный сценарий | Безопасные локализованные ошибки, текст сохранён, нет автоматического исполнения; неизвестный ID не превращается локально в валидный сценарий |
| F29 / 13 | Маскирование, отсутствие ключей и внутренних диагностик | Маскированные UI/allowlist JSON, локальное сообщение по коду; не замена серверной защите |
| F30 / 13 | Освободить микрофон/аудио после завершения | Ресурсы завершаются при end/reset/disconnect/unmount; физический индикатор устройства проверить вручную |
| F31 / 14 | Клавиатура, aria-label/live, focus, не только цвет | Реализованные контроли; полный WCAG-аудит не заявлен |
| F32 / 14 | RU/KK, переносы, 320 px, проектор, Chrome | Адаптивная компоновка и язык; контраст/zoom/реальный проектор и финальный Chrome-прогон отдельно |
| F33 / 18 | Общая команда и готовность к демонстрации | Клиентский QA воспроизводим; окончательная демонстрационная готовность остаётся открытой до B01–B15 |

Точные внутренние имена состояний и рекомендуемая структура папок в функциональном плане не являются отдельными банковскими критериями. Отсутствующий серверный этап не заменяется фиктивным UI-индикатором ради формального совпадения.

## 3. Дополнительные возможности

| Возможность | Статус и значение |
| --- | --- |
| Копирование/экспорт трассы, фильтры по языку/сценарию/статусу | Реализовано на клиенте; только разрешённые поля и маскированные значения |
| Сессионные медианы, количество ошибок/уточнений/handoff | Реализовано; это операционные статусы, **не** точность маршрутизации без эталонных labels |
| История, очередь/возврат, слоты, handoff | UI реализован; бизнес-логика у backend. В банке перечислены как развитие, команда включила в свой функциональный план |
| Потоковая обработка и автоматическое окончание речи | Клиентские части есть; выигрыш/качество на живом голосе ещё не доказаны |

| Редактор каталога без разработчика | Не реализован; нет CRUD/версий/валидации/авторизации API, не must-have банка |
| Определение эмоций и адаптация тона | Не реализованы; нет модели/согласованного поля; не must-have |
| Автоматический проигрыватель `dialogs_sample.json` | Не реализован как продуктовый UI; fixture-команды — не проигрыватель датасета. Полезен после интеграции, не must-have |
| Точность/ошибки по каждому сценарию и сравнение моделей | Требует реальных predictions, эталона и `evaluate.py`; клиентские счётчики не заменяют оценщик |

### Прикладная проверка из README датасета

- Жюри зачитывает 10 одинаковых для команд **скрытых** реплик; до 3 баллов за каждую: основной сценарий, все намерения для multi-intent (иначе правильный язык ответа), качество ответа на основе данных.
- Максимум этой части — 30, не отдельное доказательство получения 100 по общей таблице. Документы не описывают формулу объединения шкал; не складывать их произвольно.
- Бонус по **медиане всего проверочного голосового набора** от конца речи до начала звука: ≤1500 мс → +2, ≤3000 мс → +1, >3000 мс → 0. Медленное решение не снижает базовую оценку.
- Router 500 мс — ориентир, не отдельное условие допуска. Backend timing, текстовый ввод, replay, fixture и статичный пример не заменяют живой замер.
- Персоны скрытого набора используют клиентов из `mock_backend.json`; идентификация и ответы должны основываться на этих данных.
- Предсказать точность hidden-набора нельзя. Dev-прогон 104 реплик полезен для качества, но не равен итоговой оценке.

## 5. Что блокирует честное «всё ТЗ выполнено»

1. Настоящий backend по контракту: LLM-маршрутизация, состояние диалога, слоты, действия и подтверждение, handoff, факты/дата среза.
2. Реальные STT/TTS и end-to-end на микрофоне/динамике с RU/KK/mixed и всеми ошибочными путями.
3. Одна команда полного приложения и воспроизводимый прогон из свежей рабочей копии.
4. Результаты `evaluate.py` и десяти размеченных диалогов; затем реальная демонстрационная приёмка, а не fixture.
5. Измерение и публикация честных голосовых таймингов; безопасность/идемпотентность доказываются серверными тестами.

Оставшиеся frontend/device пункты перечислены без галочек в [чек-листе](frontend-verification.md). Их закрывают только после фактического выполнения. Внешние гарантии качества, баллов, WCAG или production-готовности сейчас не заявляются.
