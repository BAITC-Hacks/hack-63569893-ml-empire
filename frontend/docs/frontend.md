# Frontend: подключение к Voice Router

Статус: клиент реализован в каталоге `frontend/`, инструкции запуска и ограничения описаны в [README](../README.md). Backend разрабатывается отдельно; соответствие объединённых веток этому контракту требует интеграционной проверки. План находится в [backend implementation plan](../../docs/superpowers/plans/2026-09-23-voice-router-backend.md), общая схема — в [архитектуре](../../docs/voice-router-architecture.md). Отдельный fixture-сервер предназначен только для проверки подключения и не реализует бизнес-логику.

Этот документ — актуальный wire protocol. Имена из раннего [функционального плана](frontend-functions.md), например `call.start`, `confirmation.required` и `confirmation.submit`, не отправляются: создание сессии выполняет HTTP, подтверждение передаётся как обычная новая реплика. На сервере `thread_id` графа соответствует публичному `session_id`.

## Что должен показывать интерфейс

- Клиентский экран: кнопка записи «Нажать и говорить», текстовое поле как резервный ввод, транскрипт, ответ бота и состояние воспроизведения. Язык ответа выбирает бэкенд по речи клиента.
- Панель супервизора после каждой реплики: основной и дополнительные сценарии, альтернативы, краткая причина выбора, слоты, действия (`preview`/`execute`), статус уточнения или перевода оператору и задержка по этапам.
- Явное сообщение, что голос синтезирован ИИ; демонстрация использует только синтетическую Saqta Insurance. Реальные персональные данные вводить нельзя. Секреты LLM/STT/TTS в браузер не передаются.

Основной режим — **push-to-talk**: пользователь нажимает кнопку для начала записи и отпускает для завершения реплики. Опциональный клиентский детектор тишины использует тот же протокол; ручное завершение остаётся доступным. Браузер отправляет `turn.commit` только после последнего аудиофрейма. Настройка автозавершения не запускает микрофон без явного действия пользователя. Детектор уровня/тишины не определяет смысл, язык или сценарий.

## Адреса и подключение

Все пути имеют префикс `/api/v1`. Для локальной разработки фронт использует `VITE_API_BASE_URL=http://localhost:8000` либо прокси dev-сервера. WebSocket строится из того же origin с заменой `http` на `ws` и `https` на `wss`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/health` | Проверка доступности API: `{"status":"ok"}`. |
| `GET` | `/api/v1/catalog/scenarios` | Краткий каталог `[{"scenario_id":"SC01","name":"...","priority":"normal"}]` для панели. |
| `POST` | `/api/v1/sessions` | Создать звонок; тело `{}`. |
| `GET` | `/api/v1/sessions/{session_id}` | Восстановить краткое состояние и последнюю трассировку после перезагрузки страницы. |
| `WS` | `/api/v1/sessions/{session_id}/stream` | Реплики, аудио и события интерфейса. |

`GET /sessions/{session_id}` возвращает `session_id`, `last_seq`, `last_turn_id`, `active_scenario`, `pending_confirmation` (только безопасное резюме или `null`) и `last_trace`. Несуществующая сессия возвращает HTTP `404`; после перезапуска однопроцессного демо нужно создать новую.

Ответ восстановления и `session.ready` должны содержать ID запрошенной сессии. Для восстановления классификации передавайте **`last_trace.route` целиком в форме `route.decision.payload`**, включая обязательные `scenarios`, `alternatives`, `language`. `last_trace.transcript` принимает строку либо объект `{text, language}`. Указанный в корне snapshot `active_scenario` является авторитетным и не превращается в выдуманный основной сценарий. Этот endpoint не является архивом и не гарантирует возврат текста ответа, аудио, времени начала звонка или terminal-статуса предыдущей реплики.

Пример snapshot, который восстанавливает исходный транскрипт, классификацию и контекст:

```json
{
  "session_id": "0f44f6b2-0d24-4e31-acd1-5d7c8c9fc1db",
  "last_seq": 9,
  "last_turn_id": "e54c4ce0-4976-4604-b21b-d31b7f2be6d8",
  "active_scenario": "SC11",
  "pending_confirmation": null,
  "last_trace": {
    "transcript": {"text": "Кеше көлігімді соғып кетті, КАСКО бар. Нужен осмотр.", "language": "mixed"},
    "route": {
      "scenarios": [{"scenario_id": "SC13", "reason": "Клиент упоминает ущерб по КАСКО"}],
      "alternatives": ["SC11"],
      "language": "mixed",
      "source": "continuation",
      "active_scenario": "SC11",
      "pending_scenarios": ["SC20"],
      "suspended_scenarios": ["SC13"],
      "slots": {"insurance_type": "КАСКО"}
    },
    "actions": [],
    "latency_ms": {"stt": 210, "router": 540, "total": 1280},
    "client_first_audio_ms": 1410,
    "handoff": null
  }
}
```

`scenarios`, `alternatives`, `reason`, `source` на верхнем уровне `last_trace` **не заменяют `last_trace.route`** при восстановлении основного выбора. Отдельные top-level `pending_scenarios`, `suspended_scenarios`, `slots` и `handoff` могут отображаться панелью как данные трассы, но для полного восстановления маршрута следует использовать вложенный `route`. Если route не передан/невалиден, frontend сохраняет известный маршрут текущей страницы либо показывает отсутствие классификации; активный сценарий при этом может быть известен.

Endpoint завершения/удаления серверной сессии пока не согласован. Кнопка «Завершить» останавливает локальные ресурсы и соединение, удаляет данные восстановления, сохраняет историю текущей страницы; «Новый звонок» её очищает. Не отправлять выдуманный `call.end` и не заявлять удаление серверных данных.

Ответ `POST /sessions`:

```json
{
  "session_id": "0f44f6b2-0d24-4e31-acd1-5d7c8c9fc1db",
  "ws_path": "/api/v1/sessions/0f44f6b2-0d24-4e31-acd1-5d7c8c9fc1db/stream",
  "audio_input": {"encoding": "pcm_s16le", "sample_rate_hz": 24000, "channels": 1},
  "audio_output": {"encoding": "pcm_s16le", "sample_rate_hz": 24000, "channels": 1},
  "as_of_date": "2026-10-01"
}
```

Фронт хранит `session_id` в `sessionStorage` до завершения звонка. На каждой новой реплике создаёт UUID `turn_id`; повторная отправка того же `turn_id` не должна повторять действие. После открытия WebSocket сервер отправляет `session.ready`. Потеря соединения во время записи отменяет незавершённую реплику; после переподключения фронт получает состояние через `GET /sessions/{id}` и предлагает записать её заново.

В реализации `useVoiceSession` управляет звонком/сокетом, `api.ts` проверяет формат, `PcmRecorder`/`PcmPlayer` управляют аудио, модели состояния отделены от панели супервизора. UI различает подготовку микрофона, запись, обработку, воспроизведение и состояния соединения. Исправимая ошибка голоса оставляет доступным текст после завершения текущей реплики. Детальные AI-этапы вроде `identifying`/`executing_action` нельзя имитировать таймерами: нынешний обязательный протокол не содержит отдельного `agent.state`.

## Формат WebSocket

Управляющие сообщения — текстовые JSON-фреймы, аудио — бинарные фреймы без base64. У каждого серверного JSON-события есть оболочка:

```json
{
  "type": "route.decision",
  "turn_id": "e54c4ce0-4976-4604-b21b-d31b7f2be6d8",
  "seq": 4,
  "payload": {}
}
```

`seq` монотонно растёт в пределах сессии. `turn_id` у `session.ready` равен `null`. Фронт принимает события в порядке WebSocket, привязывает их к `turn_id` и игнорирует дубликаты/устаревшие значения `seq`. Snapshot может уже включать события, пришедшие перед восстановлением; их повтор не должен изменять состояние второй раз.

### Из браузера на сервер

| `type` | `payload` | Когда отправлять |
| --- | --- | --- |
| `turn.start` | `{"mode":"audio"}` | Сразу после начала записи, с новым `turn_id`. |
| Бинарный фрейм | PCM16 little-endian, mono, 24 kHz | Во время активной записи; фреймы идут строго после `turn.start`. |
| `turn.commit` | `{}` | После отправки последнего аудиофрейма. |
| `turn.text` | `{"text":"..."}` | Вместо аудио для резервного текстового ввода, с новым `turn_id`. |
| `playback.started` | `{"latency_ms":1234}` | При старте первого звука исходного ответа, не replay; локальное время от границы завершения ввода. |

Пример текстовой реплики:

```json
{"type":"turn.text","turn_id":"e54c4ce0-4976-4604-b21b-d31b7f2be6d8","payload":{"text":"Кеше көлігімді соғып кетті, КАСКО бар"}}
```

Браузер получает звук микрофона через `getUserMedia`. Устройства часто выдают 48 kHz float PCM, поэтому `AudioWorklet` должен свести поток к mono, передискретизировать до 24 kHz и упаковать signed 16-bit little-endian. `MediaRecorder` обычно выдаёт сжатый контейнер, который **не соответствует** указанному бинарному протоколу. Пока сервер отвечает, кнопку записи блокируем: первая версия обрабатывает один активный `turn_id` на сессию.

Если пользователь завершил/отпустил запись ещё до `turn.start`, например пока открыт запрос разрешения, подготовка отменяется. Позднее разрешение не начинает запись само: поток освобождается, показывается безопасный `recording_cancelled`, пустой `turn.commit` не отправляется. Для записи после предоставления разрешения необходимо новое действие пользователя.

### С сервера в браузер

| `type` | Основные поля `payload` | Действие фронта |
| --- | --- | --- |
| `session.ready` | `session_id`, `last_seq` | Разрешить ввод. |
| `transcript.partial` | `text` | Обновить черновой транскрипт без запуска диалога. |
| `transcript.final` | `text`, `language` (`ru`, `kk`, `mixed` или `null`) | Зафиксировать исходную реплику; `route.decision.language` уточняет язык запроса, `agent.text.language` — язык ответа. |
| `route.decision` | `scenarios`, `alternatives`, `reason`, `language`, `slots`, `source` | Обновить панель супервизора; массив сценариев упорядочен. `source` — `llm`, `continuation` или `confirmation`. |
| `action.preview` | `name`, `summary`, `masked_args` | Показать ожидаемое подтверждение; само действие ещё не выполнялось. |
| `agent.text` | `text`, `language` | Показать ответ сразу, даже если TTS ещё работает. |
| `audio.start` | `encoding`, `sample_rate_hz`, `channels` | Подготовить декодер и очередь воспроизведения. |
| Бинарный фрейм | PCM16 little-endian, mono, 24 kHz | Добавить в очередь воспроизведения в порядке получения. |
| `audio.end` | `{}` | Завершить поток после проигрывания очереди. |
| `trace.updated` | `actions`, `latency_ms`, `handoff` | Обновить трассировку и тайминги. |
| `turn.complete` | `status` (`answered`, `clarify`, `handoff`, `error`) | Завершить серверную обработку; новый ввод доступен после окончания/остановки аудио. |
| `error` | `code`, `message`, `recoverable` | Показать безопасный локализованный текст по коду, не сырую внутреннюю диагностику. |

Бинарные фреймы **от сервера** относятся к последнему `audio.start` до `audio.end`. Бинарные фреймы **от клиента** относятся к открытому `turn.start` до `turn.commit`. Одновременно открывается только одна аудиореплика, поэтому отдельный заголовок в бинарном фрейме не нужен.

`route.decision` приходит после **каждой** финальной реплики. Для ответа на вопрос о слоте и для подтверждения `source` показывает, что граф продолжил активный сценарий без нового LLM-вызова. `scenarios` имеет форму `[{"scenario_id":"SC13","reason":"...","confidence_estimate":0.83}]`; `confidence_estimate` — оценка модели для интерфейса, не калиброванная вероятность.

### Дополнительные поля для полной панели

Frontend отображает следующие расширения, когда они присутствуют. Это обратно совместимое расширение базового контракта, не утверждение, что подключённый сервер уже их выдаёт. Отсутствие поля и явные `null`/пустой список различаются; клиент не вычисляет бизнес-состояние самостоятельно.

| Поле | Форма и смысл |
| --- | --- |
| `route.decision.active_scenario` | ID, объект сценария или `null`; **не обязательно** первый элемент `scenarios` |
| `pending_scenarios`, `suspended_scenarios` | Массивы ID/объектов в серверном порядке; frontend не пересортировывает выбор |
| `is_continuation` | Явный boolean; `source=continuation` также обозначает продолжение |
| Сценарий | Дополнительно `name`, `priority` (`normal`, `high`, `urgent`), `reason`, `confidence_estimate` |
| `slots` | Объект: имя → простое значение либо `{value, status, source, scenario_id}`; статусы `found`, `from_profile`, `confirmed`, `missing`, `invalid` |
| `trace.updated.actions` | Строки `action:preview`/`action:execute` либо объекты `{name, mode, status, arguments, summary, error}` |
| Статус действия | `requested`, `awaiting_confirmation`, `executing`, `completed`, `rejected`/`cancelled`, `failed`; `mode=execute` сам по себе не доказывает успешное выполнение |
| `trace.updated.handoff` | `{reason, queue, status, active_scenario, slots, summary, context}`; каждое поле необязательно. `context_received` не означает подключённого оператора |
| `trace.updated.clarification` | Короткий вопрос/данные уточнения, если сервер их передаёт; иначе используется полученный ответ со статусом `clarify` |
| `trace.updated.agent_state` | Необязательное явное бизнес-состояние из словаря функционального плана; без него детальные этапы identifying/collecting/executing не имитируются |
| `trace.updated.latency_ms` | Частичное обновление этапов; новые значения объединяются с уже полученными этапами той же реплики |
| `trace.updated.affect` | Аддитивное предложение ниже: эмоция, тон ответа, источник, оценка. Необходимо согласовать и реализовать серверное отображение |

Статусы слотов/действий и handoff следует согласовать с сервером до интеграции. Неизвестное значение показывается как неизвестное, а не преобразуется в успех. Для полноценного восстановления повторите маршрут с очередями/слотами в **`last_trace.route`**, как в примере snapshot выше.

Ответ с подтверждением выглядит так: `action.preview` → `agent.text`/аудио с просьбой подтвердить → `turn.complete`. Следующее произнесённое «да» или «иә» отправляется как **новая реплика**; только бэкенд решает, достаточно ли ответа для выполнения действия. Реализованные кнопки отправляют обычный `turn.text`: «Да, подтверждаю» / «Иә, растаймын» либо «Нет, отказываюсь» / «Жоқ, бас тартамын». Решение видно в истории. Нет клиентского вызова execute, автоматического согласия или повторного исполнения при reconnect.

## Воспроизведение и задержка

Воспроизведение запускается после действия пользователя, чтобы браузер разрешил аудио. Фронт создаёт `AudioContext`, преобразует входящий PCM16 в float и ставит чанки в последовательную очередь. При отпускании кнопки он сохраняет `endOfSpeechAt = performance.now()` и только затем досылает остаток аудио и `turn.commit`. После фактического старта первого чанка он считает `performance.now() - endOfSpeechAt` и посылает `playback.started`. Не смешивать этот клиентский показатель с серверным временем отправки первого чанка: в панели можно показывать оба, но бонус оценивается по реальному первому звуку.

Пример `trace.updated`:

```json
{
  "type": "trace.updated",
  "turn_id": "e54c4ce0-4976-4604-b21b-d31b7f2be6d8",
  "seq": 9,
  "payload": {
    "actions": ["find_client", "create_claim:preview"],
    "latency_ms": {"stt": 210, "triage": 5, "router": 540, "response": 12, "tts_first_audio": 280, "total": 1280},
    "client_first_audio_ms": 1410,
    "handoff": null
  }
}
```

Для текстовой реплики `stt` равен `0`; `client_first_audio_ms` появляется только после события `playback.started`. Если TTS недоступен, `agent.text` остаётся видимым, сервер присылает `error` с `code="tts_unavailable"`, а реплика всё равно завершается.

В панели отдельно считаются медианы серверного total, router, первого аудио для голосовых и для текстовых реплик, с количеством валидных измерений. Отсутствующее значение не равно нулю. Replay, mute без воспроизведения и TTS-ошибка не должны создавать новый замер первого звука. При автозавершении клиент учитывает накопленный интервал тишины, а не считает начало измерения только с момента срабатывания детектора. Детектор — эвристика по аудиоуровню; точность окончания речи/первого физического звука проверяется на устройстве. Данные fixture и статичного примера не являются измерениями для баллов.

Остановка воспроизведения пользователем не является отменой серверного turn: следующие аудиочанки можно сохранить для replay, не воспроизводя их немедленно. Новый ввод остаётся заблокирован, пока сервер не завершил предыдущую обработку.

## Ошибки и восстановление

`error.code` для интерфейса: `invalid_event`, `session_not_found`, `busy`, `stt_unavailable`, `router_unavailable`, `tts_unavailable`, `action_failed`. Ошибка не является разрешением на выполнение ожидающего подтверждения действия. Нельзя автоматически повторять `turn.text` или `turn.commit` после потери соединения: сначала получить состояние сессии и проверить последний `turn_id`.

HTTP и ожидание `session.ready` ограничены 10 секундами. Отсутствие событий 60 секунд во время обработки/ответа считается зависанием: клиент закрывает соединение и получает snapshot через ограниченный reconnect, не переотправляя реплику. Это защитный timeout интерфейса, не обещание серверной производительности.

API-ключи провайдеров хранятся только на бэкенде. Для локального демо разрешён конкретный origin фронта через CORS; WebSocket проверяет origin при подключении. Реальные персональные данные использовать **нельзя**: стартовый набор синтетический. Повторное отображение и экспорт маскируют телефон, ИИН, email и чувствительные структурированные поля; это дополнительная защита, не полноценная система обезличивания. Внутренние сообщения/stack trace/секреты от сервера не должны выводиться или экспортироваться. Неизвестный код ошибки получает нейтральное сообщение.

## Очерёдность работы фронтенда

1. Подключить `POST /sessions`, текстовые `turn.text`, `agent.text`, `route.decision` и `trace.updated`; проверить смену языка и несколько сценариев.
2. Добавить микрофон, `AudioWorklet`, `turn.start`/binary/`turn.commit` и отображение частичного транскрипта.
3. Добавить PCM-воспроизведение, `playback.started`, ошибки TTS и восстановление сессии после перезагрузки.
4. Проверить живые русские, казахские и смешанные реплики из [условий кейса](../../datas/README.ru.md), а также явное согласие перед необратимым действием.

Технические основания контракта: [FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/), [OpenAI Realtime transcription](https://developers.openai.com/api/docs/guides/realtime-transcription), [OpenAI TTS](https://developers.openai.com/api/docs/guides/text-to-speech).

## Эмоции и тон: аддитивное предложение контракта

Клиентская поддержка реализована, но **наличие поля в backend не подтверждено**. Перед объединённой приёмкой backend-разработчик должен согласовать отображение результата модели в эту структуру. Нового endpoint или отдельного клиентского события не требуется; объект находится в `trace.updated.payload.affect`, при восстановлении в `last_trace.affect`.

```json
{
  "affect": {
    "emotion": "concerned",
    "response_tone": "empathetic",
    "source": "text",
    "confidence": 0.72
  }
}
```

Пример иллюстрирует форму, а не фактическую оценку пользователя.

| Поле | Допустимые значения |
| --- | --- |
| `emotion` | `neutral`, `concerned`, `frustrated`, `angry`, `sad`, `positive` |
| `response_tone` | `neutral`, `empathetic`, `calm`, `reassuring`, `concise` |
| `source` | `audio`, `text`, `multimodal` |
| `confidence` | Конечное число от 0 до 1; оценка модели, не калиброванная вероятность |

Эмоция и тон независимы: клиент показывает поддерживаемые поля, неизвестные/отсутствующие значения не выдумывает. Если не распознаны ни эмоция, ни тон, сведений для показа нет. Свободный текст психологического заключения или hidden reasoning передавать не нужно. В UI и экспорте используются только разрешённые значения.

Реальное определение эмоции, выбор тона, адаптация текста ответа и параметров TTS остаются серверными обязанностями. Фронтенд не классифицирует речь по ключевым словам и не доказывает полезность адаптации наличием метки.

## Локальные инструменты и границы API

Редактор полного каталога использует локальный JSON и экспорт, **не** существующий краткий `GET /catalog/scenarios` для записи. CRUD, публикация, версии и авторизация не согласованы; клиент не отправляет выдуманные mutating endpoints.

Диалоговый проигрыватель отправляет обычные `turn.text` только по ручному шагу, без эталонных меток/ответов. Аналитика принимает файлы predictions локально и не запускает серверный benchmark или переключение fast/full. Аудиодиагностика удерживает PCM только в памяти браузера и не использует WebSocket. Форматы и сценарии работы: [frontend-labs.md](frontend-labs.md).
