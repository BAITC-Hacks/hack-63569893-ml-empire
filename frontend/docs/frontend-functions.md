# Voice Router: функции веб-интерфейса

Статус: функциональные требования и критерии приёмки веб-симулятора Voice Router. Актуальная реализация и остаточные зависимости перечислены в [матрице покрытия](requirements-coverage.md); инструкция запуска — в [общем README](../../README.md#live). Этот документ не является отчётом об успешном прохождении живой приёмки.

Уточнение объёма от 23.09.2026: пользователь включил **все обязательные и опциональные пункты исходного ТЗ банка**, а не любые дополнения внутреннего плана. Проигрыватель датасета, отдельная аудиодиагностика и статичный пример удалены как добавленные сверх ТЗ. Серверные AI-модели и публикация каталога остаются ответственностью backend. Реализованные редактор и аналитика описаны в [frontend-labs.md](frontend-labs.md).

Документ описывает пользовательские функции, состояния интерфейса, рекомендуемые React-модули и контракт взаимодействия с сервером. Источники: техническое задание кейса, [архитектура решения](../../docs/voice-router-architecture.md) и файлы стартового набора в [`datas`](../../datas). Это детализация реализации: названия экранов, контролы, локальные форматы и рекомендации по коду не являются отдельными дословными требованиями банка.

Имена функций и TypeScript-модели ниже описывают логические обязанности, не обязательные имена файлов/экспортов. `thread_id` — внутренний ID графа, соответствующий `session_id` в публичном API. **Wire protocol определяется только [frontend.md](frontend.md)**; ранние рекомендации по отдельным событиям заменены согласованным HTTP/WebSocket-контрактом.

## 1. Цель фронтенда

Фронтенд должен предоставить два связанных рабочих пространства:

1. Интерфейс клиента для голосового разговора с AI-роботом.
2. Панель супервизора для просмотра решений маршрутизатора после каждой реплики.

Основной пользовательский путь:

1. Пользователь начинает новый звонок.
2. Разрешает доступ к микрофону.
3. Произносит реплику на русском, казахском или смешанном языке.
4. Интерфейс передаёт аудио серверу и показывает промежуточный или финальный транскрипт.
5. Сервер выбирает один или несколько сценариев и возвращает трассировку.
6. Интерфейс показывает короткий ответ робота и начинает воспроизведение аудио.
7. Панель супервизора показывает выбранные сценарии, обоснование, слоты, действия и задержки.
8. Диалог продолжается в рамках одного `thread_id` до завершения звонка или передачи оператору.

## 2. Обязательные пользовательские функции

### 2.1 Управление звонком

Интерфейс должен позволять:

- начать новый звонок;
- получить от сервера `thread_id`;
- завершить активный звонок;
- начать новый звонок с полностью очищенным состоянием;
- восстановить активную сессию после краткого разрыва соединения;
- видеть длительность звонка и текущее состояние соединения.

После завершения звонка история текущей сессии остаётся доступна для просмотра, пока пользователь не начал новый звонок. В текущем контракте завершение является клиентским: останавливаются микрофон, звук, сокет и восстановление. Серверный endpoint завершения/удаления сессии не согласован; frontend не заявляет удаление данных на сервере.

Рекомендуемые функции:

```ts
async function startCall(): Promise<CallSession>
async function endCall(threadId: string): Promise<void>
async function resetCall(): Promise<void>
async function reconnectCall(threadId: string): Promise<void>
```

### 2.2 Работа с микрофоном

Голос является основным каналом ввода. Интерфейс должен:

- запросить разрешение браузера на использование микрофона;
- начать и остановить запись;
- показать, что робот слушает пользователя;
- показать уровень входного аудиосигнала;
- передавать аудиофрагменты серверу;
- определить окончание реплики или предоставить кнопку ручного завершения;
- освободить микрофон после завершения звонка;
- не записывать аудио до явного действия пользователя.

Обязательные состояния:

- `permission_required`;
- `permission_denied`;
- `microphone_unavailable`;
- `ready`;
- `recording`;
- `finishing_utterance`;
- `uploading_audio`;
- `stt_processing`;
- `error`.

Рекомендуемые функции:

```ts
async function requestMicrophonePermission(): Promise<PermissionState>
async function listAudioInputDevices(): Promise<MediaDeviceInfo[]>
async function startRecording(): Promise<void>
async function stopRecording(): Promise<void>
function handleAudioChunk(chunk: Blob): void
function detectSpeechEnd(level: number, timestamp: number): boolean
function releaseMicrophone(): void
```

Клиентское определение окончания речи должно быть настраиваемым и не должно обрезать тихие окончания фраз. Ручная кнопка завершения реплики остаётся обязательным резервным способом.

Реализованные настройки в разговоре: пауза 800–2500 мс и порог речи RMS 0.005–0.08. Низкий порог помогает тихому голосу, но может принимать шум за речь. Начальная тишина не считается завершившейся репликой. Корректность записи и воспроизведения требует фактической проверки устройства, а не только наличия настроек.

### 2.3 Текстовый резервный канал

Текст дополняет голос, но не заменяет его в основной демонстрации. Интерфейс должен:

- принимать пользовательский текст;
- запрещать отправку пустой строки;
- отправлять текст в тот же `thread_id`;
- блокировать повторную отправку во время обработки;
- позволять повторить отправку после сетевой ошибки;
- сохранять текстовую реплику в общей истории диалога.

Рекомендуемые функции:

```ts
async function sendTextMessage(text: string): Promise<void>
function normalizeTextInput(text: string): string
function canSubmitText(text: string, callState: CallState): boolean
```

Нормализация на клиенте ограничивается пробелами и безопасной подготовкой строки. Телефоны, даты, номера полисов и другие бизнес-значения нормализует сервер.

### 2.4 Транскрипт

Для голосовой реплики интерфейс должен отображать:

- промежуточный транскрипт, если он поступает;
- финальный транскрипт;
- язык `ru`, `kk` или `mixed`;
- признак, что распознавание завершено;
- ошибку STT без удаления исходной реплики из истории.

Смешанную речь необходимо показывать в исходном виде. Фронтенд не переводит и не переписывает транскрипт.

Рекомендуемые функции:

```ts
function updatePartialTranscript(turnId: string, text: string): void
function finalizeTranscript(turnId: string, text: string, language: Language): void
function markTranscriptError(turnId: string, error: ClientError): void
```

### 2.5 История диалога

История должна содержать до 10 пользовательских реплик и соответствующие ответы робота. Для каждой записи отображаются:

- автор: клиент или робот;
- текст;
- язык;
- время;
- состояние доставки или обработки;
- кнопка повторного воспроизведения ответа робота;
- связанная трассировка для реплики клиента.

Новая реплика автоматически прокручивает страницу к концу диалога только когда пользователь уже находится внизу; ручная позиция чтения истории не сбрасывается. Чат растёт по содержимому без отдельного скроллера. На широком экране панель трассировки остаётся рядом благодаря `position: sticky`, на телефоне области переключаются и прокручиваются со страницей.

Рекомендуемые функции:

```ts
function appendUserTurn(turn: UserTurn): void
function appendAssistantTurn(turn: AssistantTurn): void
function updateTurnStatus(turnId: string, status: TurnStatus): void
function scrollToLatestTurn(options?: { force?: boolean }): void
```

### 2.6 Голосовой ответ

Интерфейс должен:

- получать текст ответа;
- получать поток аудио или ссылку на аудио;
- начинать воспроизведение как можно раньше;
- зафиксировать момент начала первого аудиофрагмента;
- позволять остановить, повторить и отключить звук;
- корректно обработать запрет браузера на автоматическое воспроизведение;
- сохранить текстовый ответ доступным при ошибке TTS.

Рекомендуемые функции:

```ts
function enqueueAudioChunk(turnId: string, chunk: ArrayBuffer): void
async function playAssistantAudio(turnId: string): Promise<void>
function pauseAssistantAudio(): void
function replayAssistantAudio(turnId: string): void
function setMuted(muted: boolean): void
function recordFirstAudioPlayback(turnId: string, timestamp: number): void
```

## 3. Состояния работы агента

Фронтенд не вычисляет бизнес-состояние самостоятельно. Он отображает состояние, полученное от сервера. Перечень ниже — целевой словарь бизнес-состояний, не набор событий уже существующего API: отдельного `agent.state` в обязательном контракте сейчас нет. Реально различаются подготовка микрофона, запись, обработка, воспроизведение, соединение и терминальные результаты; `identifying`, `collecting_slots`, `executing_action` можно показывать только по явным серверным данным, не по выдуманному таймеру.

Поддерживаемые состояния:

| Состояние | Отображение для клиента |
| --- | --- |
| `idle` | Можно начать разговор |
| `listening` | Робот слушает |
| `transcribing` | Распознаём речь |
| `routing` | Определяем запрос |
| `identifying` | Уточняем клиента |
| `collecting_slots` | Собираем необходимые данные |
| `awaiting_confirmation` | Ожидается явное подтверждение |
| `executing_action` | Выполняется действие |
| `responding` | Робот готовит ответ |
| `speaking` | Робот отвечает голосом |
| `handoff` | Разговор передаётся оператору |
| `completed` | Звонок завершён |
| `error` | Произошла ошибка, доступен безопасный вариант продолжения |

Рекомендуемые функции:

```ts
function applyAgentState(state: AgentState): void
function getAgentStateLabel(state: AgentState, language: UiLanguage): string
function isInputAllowed(state: AgentState): boolean
```

## 4. Панель трассировки

После каждой финальной реплики клиента панель супервизора должна создать отдельную запись с постоянным `turn_id`. Текст финального транскрипта не заменяется следующей репликой; потоковые trace/тайминги дополняют только свою запись. Старая трасса не подменяется текущим глобальным состоянием.

### 4.1 Обязательные поля

- номер реплики;
- финальный транскрипт;
- язык;
- основной сценарий;
- дополнительные сценарии;
- альтернативы;
- краткое обоснование;
- `is_continuation`;
- найденные слоты;
- источник каждого слота, если сервер его возвращает;
- запрошенные действия;
- действия в режиме `preview`;
- выполненные действия;
- состояние подтверждения;
- активный сценарий;
- очередь ожидающих сценариев;
- прерванные сценарии;
- факт уточнения;
- факт передачи оператору;
- ошибки;
- задержка по этапам.

Рекомендуемые функции:

```ts
function appendTrace(trace: TurnTrace): void
function updateTrace(turnId: string, patch: Partial<TurnTrace>): void
function selectTrace(turnId: string): void
function copyTraceAsJson(turnId: string): Promise<void>
function formatScenarioLabel(scenario: ScenarioRef): string
function formatSlotValue(slot: TraceSlot): string
```

### 4.2 Отображение сценариев

Основной сценарий отображается наиболее заметно: `SC13 · Заявление об ущербе по КАСКО`.

Дополнительно нужно показывать:

- уровень приоритета `normal`, `high` или `urgent`;
- остальные намерения в порядке обработки;
- альтернативы отдельно от выбранных сценариев;
- короткую причину выбора;
- оценку модели, если она есть.

Оценку модели нельзя подписывать как гарантированную вероятность правильности. Допустимые названия: «оценка модели» или `model confidence`.

### 4.3 Слоты и действия

Для слотов нужны статусы:

- найден;
- взят из профиля;
- подтверждён пользователем;
- отсутствует;
- отклонён как некорректный.

Для действий нужны статусы:

- запрошено;
- подготовлено для подтверждения;
- ожидает подтверждения;
- выполняется;
- выполнено;
- отменено клиентом;
- завершилось ошибкой.

Персональные данные при повторном отображении необходимо маскировать.

## 5. Задержки и метрики

Для каждой реплики отображаются:

```ts
interface LatencyMetrics {
  stt: number;
  triage: number;
  router: number;
  response: number;
  tts_first_audio: number;
  total: number;
}
```

`total` измеряется от конца речи клиента до начала воспроизведения первого аудиофрагмента.

Интерфейс должен:

- показывать значения в миллисекундах;
- выделять `total`;
- визуально показывать последовательность этапов;
- считать медиану `total` по текущей сессии;
- не подменять серверные замеры произвольным клиентским временем;
- при наличии обоих замеров отдельно обозначать server timing и browser timing.

Рекомендуемые функции:

```ts
function renderLatencyTimeline(metrics: LatencyMetrics): void
function calculateMedianTotal(traces: TurnTrace[]): number | null
function getLatencyStatus(totalMs: number): "excellent" | "acceptable" | "slow"
```

Ориентиры:

- до 1 500 мс — максимальный бонус;
- от 1 500 до 3 000 мс — частичный бонус;
- более 3 000 мс — без бонуса, но без снижения основной оценки.

## 6. Несколько намерений и смена темы

Интерфейс должен отображать три отдельные группы:

- `active_scenario` — текущая задача;
- `pending_scenarios` — следующие задачи текущего запроса;
- `suspended_scenarios` — задачи, прерванные сменой темы.

Правила отображения:

- `urgent` показывается первым;
- остальные сценарии сохраняют порядок упоминания;
- прерванный сценарий не исчезает;
- после завершения новой темы пользователь видит предложение вернуться к старой;
- продолжение ожидаемого ответа не создаёт визуально новый независимый звонок или сценарий.

Рекомендуемые функции:

```ts
function updateScenarioQueue(state: ScenarioQueueState): void
function getActiveScenario(): ScenarioRef | null
function getPendingScenarios(): ScenarioRef[]
function getSuspendedScenarios(): ScenarioRef[]
```

## 7. Подтверждение необратимых действий

При согласованном событии `action.preview` (либо восстановленном `pending_confirmation`) интерфейс должен:

1. Остановить автоматическую отправку других команд действия.
2. Показать название действия и проверенные аргументы.
3. Предложить подтвердить или отказаться голосом.
4. Продублировать выбор кнопками «Подтвердить» и «Отказаться».
5. Отправить решение в существующий `thread_id`.
6. Дождаться серверного подтверждения выполнения.

Кнопки согласия/отказа отправляют новую `turn.text` с явным текстом на выбранном языке; голос идёт обычной новой аудиорепликой. Отдельные события `confirmation.required`/`confirmation.submit` были ранним предложением и не используются.

Фронтенд не имеет права самостоятельно считать действие выполненным после нажатия кнопки.

Рекомендуемые функции:

```ts
function showConfirmation(request: ConfirmationRequest): void
async function confirmAction(confirmationId: string): Promise<void>
async function rejectAction(confirmationId: string): Promise<void>
function clearConfirmation(): void
```

## 8. Уточнение и передача оператору

При неясном запросе интерфейс показывает один короткий вопрос робота. Одновременно задавать несколько вопросов нельзя.

При передаче оператору показываются:

- понятное сообщение клиенту;
- причина передачи;
- очередь или направление оператора;
- активный сценарий;
- собранные слоты;
- краткое резюме контекста;
- статус передачи.

Рекомендуемые функции:

```ts
function showClarification(question: string): void
function showHandoff(summary: HandoffSummary): void
function updateHandoffStatus(status: HandoffStatus): void
```

## 9. Ошибки и восстановление

### 9.1 Ошибки микрофона

- доступ запрещён;
- устройство отсутствует;
- устройство отключено во время звонка;
- браузер не поддерживает нужный API;
- запись неожиданно завершилась.

Пользователю показывается понятное действие: повторить запрос разрешения, выбрать другое устройство или перейти на текст.

### 9.2 Ошибки сети и сервера

- потеря WebSocket;
- таймаут запроса;
- сервер недоступен;
- неизвестный `thread_id`;
- повторное получение одного события;
- нарушение порядка событий.

Клиент должен поддерживать повторное подключение с ограниченным количеством попыток и защитой от дублирования событий.

### 9.3 Ошибки AI-конвейера

- STT не распознал речь;
- LLM вернул некорректную структуру;
- выбран неизвестный сценарий;
- маршрутизация неуверенная;
- TTS недоступен;
- действие вернуло доменную ошибку.

Ошибка STT, LLM или TTS не должна переводить подготовленное действие в состояние «выполнено».

Рекомендуемые функции:

```ts
function mapServerError(error: ServerError): ClientError
function showRecoverableError(error: ClientError): void
function showFatalError(error: ClientError): void
async function retryLastInput(): Promise<void>
async function reconnectWithBackoff(threadId: string): Promise<void>
function hasProcessedEvent(eventId: string): boolean
```

## 10. Актуальный контракт HTTP/WebSocket

Точные payload и валидация находятся в [frontend.md](frontend.md). Не реализовывать одновременно два протокола.

| Обязанность | Согласованный механизм |
| --- | --- |
| Создать звонок | `POST /api/v1/sessions` → `session_id` |
| Восстановить | `GET /api/v1/sessions/{session_id}` → snapshot |
| Подключить события | `WS /api/v1/sessions/{session_id}/stream` → `session.ready` |
| Голос клиента | `turn.start` → бинарные PCM16 mono 24 kHz → `turn.commit` |
| Текст/подтверждение/отказ | Новая `turn.text` с UUID `turn_id` |
| Речь в текст | `transcript.partial` / `transcript.final` |
| Маршрут | `route.decision` |
| Preview | `action.preview` |
| Ответ | `agent.text`, `audio.start` → binary PCM → `audio.end` |
| Трасса/результат | `trace.updated`, `turn.complete`, `error` |
| Первый звук | `playback.started` один раз для исходного ответа, не replay |
| Завершение звонка | Локальная остановка; серверного endpoint пока нет |

Серверная оболочка — `{type, turn_id, seq, payload}`. Монотонный `seq` в пределах сессии служит для защиты от дублей и устаревших событий, `turn_id` связывает данные с репликой. Прежние имена `call.start`, `text.submit`, `assistant.text`, `confirmation.submit`, `call.end` и оболочка с `event_id/sequence` не являются действующим контрактом.

## 13. Требования к безопасности и приватности

- Ключи LLM, STT и TTS не хранятся в браузере.
- Все внешние AI-запросы выполняет сервер.
- Фронтенд не использует реальные записи разговоров.
- Персональные значения маскируются при повторном отображении.
- Текст ошибок не должен показывать секреты, промпты или внутренний stack trace.
- Необратимое действие выполняется только после подтверждения сервера.
- После завершения звонка микрофон и аудиопотоки освобождаются.

## 14. Доступность и удобство демонстрации

- Все основные функции доступны с клавиатуры.
- Кнопка микрофона имеет текстовую подпись и `aria-label`.
- Состояние записи не обозначается только цветом.
- Транскрипт и текст ответа доступны даже при отключённом звуке.
- Динамически появляющиеся ошибки и статусы объявляются через `aria-live`.
- Контраст текста и статусов достаточен для демонстрации на проекторе.
- Интерфейс корректно работает в актуальном Chrome на ноутбуке.
- Для доступа к микрофону используется HTTPS или localhost.

## 15. Реализация опциональных требований банка

По запросу пользователя опциональные требования исходного ТЗ также входят в объём. Основание: статистика ошибок в панели супервизора, измеримый выигрыш гибридного маршрутизатора, редактирование каталога без разработчиков и эмоции/адаптация тона. Перечисленные ниже JSON-форматы, формы, фильтры и экспорт — выбранные способы реализации и проверки этих возможностей, а не дополнительные критерии банка. Состояние, ограничения и проверка перечислены в [матрице покрытия](requirements-coverage.md), инструкция и файловые схемы находятся в [frontend-labs.md](frontend-labs.md).

### 15.1 Аналитика и сравнение

- Принимать JSON-предсказания маршрутизатора по ID из `dev_utterances.json`, не отправляя их внешним сервисам.
- Считать primary accuracy, full match и multi-intent recall по формулам `datas/evaluate.py`; отсутствующие ID считать ошибками, явно показывать покрытие.
- Показать языки, типы, ошибки по сценариям, пропущенные/лишние интенты, путаницу первого сценария и список несовпадений.
- Отделять долю уточнений/выходов за область от точности; показывать знаменатель. Не подменять качество операционными счётчиками.
- Принимать только явно переданные задержки, показывать медиану и количество измерений.
- Сравнивать Full/Fast только на общих ID; время сравнивать при одинаковом явно указанном этапе. Не утверждать, что загрузка файла включает fast-path на сервере.
- Выгружать отчёт без реплик, произвольных метаданных, имён файлов или секретов.

### 15.2 Редактор каталога

- Искать сценарии, редактировать основные поля и полный JSON: примеры, ответы RU/KK, слоты, действия, исключения, приоритет и признаки маршрута.
- Создавать и удалять дополнительные сценарии; не удалять исходные SC01–SC40 и системные намерения.
- Проверять схему, уникальность, ссылки на сценарии/слоты/действия/очереди и обязательное подтверждение необратимых действий.
- Сохранять локальный черновик в браузере, импортировать/экспортировать каталог и подтверждать замену/сброс/удаление.
- Чётко отличать локальный черновик от действующего сервера. Публикация требует отдельного согласованного API, версий и контроля доступа, которых frontend не выдумывает.

### 15.3 Эмоции и тон

- Показывать эмоцию, тон ответа, источник сигнала и оценку только по серверному `trace.affect`.
- Не классифицировать пользователя локально по словам и не выдавать оценку модели за достоверный психологический вывод.
- При отсутствии/невалидности данных показывать отсутствие сведений. Словарь и аддитивное предложение контракта: [frontend.md](frontend.md#эмоции-и-тон-аддитивное-предложение-контракта).
- Определение эмоции и реальная адаптация текста/TTS принадлежат backend; отображение поля не доказывает их качество.

### 15.4 Экспорт и фильтры трассировок

Копирование/JSON-экспорт и фильтры по языку, сценарию и статусу включены в панель супервизора. Экспорт допускает только разрешённые поля, маскирует персональные значения и не раскрывает внутреннюю диагностику.

## 16. Что нельзя реализовывать на фронтенде

- Выбор сценария по ключевым словам или локальным `if/else`.
- Хардкод соответствия тестовых реплик сценариям.
- Обученный intent-классификатор для выбора бизнес-сценария.
- Самостоятельное выполнение мок-действий без ответа сервера.
- Автоматическое подтверждение необратимого действия.
- Подстановка фактов, отсутствующих в серверном ответе.
- Хранение секретных API-ключей.
- Представление `model confidence` как гарантированной вероятности правильного ответа.

## 17. Порядок реализации

### Этап 1. Текстовый прототип

- Создать React-приложение.
- Реализовать двухпанельный layout.
- Подключить создание `thread_id`.
- Реализовать текстовый ввод.
- Показать историю диалога и трассировку.
- Обработать несколько сценариев, слоты, действия и ошибки.

### Этап 2. Диалоговые состояния

- Реализовать очередь сценариев.
- Показать смену темы и возврат к прерванной теме.
- Реализовать уточнение.
- Реализовать подтверждение необратимых действий.
- Реализовать handoff.

### Этап 3. Голос

- Подключить микрофон.
- Передавать аудиофрагменты.
- Показывать промежуточный и финальный транскрипт.
- Подключить потоковый TTS.
- Реализовать ручное и автоматическое завершение реплики.

### Этап 4. Метрики и устойчивость

- Показать задержки по этапам.
- Рассчитать медиану `total`.
- Реализовать восстановление WebSocket.
- Защититься от повторных событий.
- Проверить ошибки микрофона, STT, LLM, TTS и действий.

### Этап 5. Демонстрационная проверка

- Русская реплика.
- Казахская реплика.
- Смешанная речь.
- Два намерения в одной реплике.
- Смена темы.
- Возврат к прерванной теме.
- Уточнение.
- Идентификация клиента.
- Подтверждение и отказ от действия.
- Передача оператору.
- Ошибка голосового канала с рабочим текстовым резервом.
- Трассировка и задержки после каждой реплики.

## 18. Критерии готовности фронтенда

Фронтенд считается готовым к демонстрации, если:

- жюри может начать звонок и говорить через микрофон;
- робот отвечает голосом, а текст остаётся видимым;
- русский, казахский и смешанный ввод не ломают интерфейс;
- после каждой реплики появляется полная трассировка;
- несколько сценариев отображаются раздельно и в правильном порядке;
- смена темы не удаляет предыдущий контекст из UI;
- необратимое действие невозможно выполнить без подтверждения;
- передача оператору отображает контекст и причину;
- значения задержки видны и не смешиваются между репликами;
- при ошибке голоса пользователь может продолжить текстом;
- переподключение не дублирует сообщения и действия;
- в браузерной сборке отсутствуют секретные ключи;
- проект запускается общей командой, описанной в README.
- доступны клиентские процессы раздела 15; серверные зависимости явно обозначены, локальный черновик или импортированный результат не выдаётся за подтверждённое выполнение backend;
- физические и браузерные проверки зафиксированы в [чек-листе](frontend-verification.md), а непроверенные условия не объявлены пройденными.
